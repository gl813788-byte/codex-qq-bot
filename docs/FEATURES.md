# Features

[简体中文](FEATURES_CN.md) | English

Codex QQ Bot is a local message hub: OneBot provides QQ transport, the Hub owns permissions, context, tools, memory and delivery, and Codex CLI performs reasoning and tasks. QQ, NapCat and LLBot binaries are not distributed by this repository.

## QQ transport and triggers

- OneBot 11 HTTP API and reverse HTTP webhooks.
- Group traffic is limited to `qq.allowedGroups`; private and group chats have separate context.
- Ordinary group messages trigger on mention, reply to the Bot or a poke targeting the Bot.
- Recognized slash commands do not require a mention inside allowlisted groups. Proactive interest uses a separate constrained path.
- Message, user and group IDs are normalized, and duplicate OneBot events are dropped before domain policy.
- Current-scope reply context identifies human speakers as `current group card/nickname + QQ number`. Mention targets retain their QQ numbers and are enriched from the current group's member profile when an inline name is unavailable. One QQ number remains the stable person identity across groups, while different group cards remain group-scoped.
- JSON/XML share cards and nested merged-forward records become bounded, readable, untrusted context.

## Codex Agent reply path

Every normal QQ reply uses the same Agent pipeline:

```text
trigger policy
  -> recent and related chat, images and memory
  -> native Codex App Server thread/turn
  -> native Web Search, files, shell and dynamic QQ tools as needed
  -> structured final response
  -> text/image/file/sticker/multi-bubble delivery
```

A simple conversation can finish without tools. For harder work, Codex owns the native multi-turn Agent loop, planning, context compaction, file/shell operations and Web Search. The Hub contributes experimental App Server dynamic tools for QQ history, scoped memory, knowledge, Chinese-search fallback and real QQ actions. Every dynamic call is bound to the original event and sender permissions; owner-only runtime controls are never exposed to an unverified sender. During a longer task, up to four distinct native commentary updates can be delivered immediately through the same receipt-bearing QQ path and remembered as Bot output; plans, empty messages, stale markers and final-schema JSON are never exposed as progress. The final answer remains a strict JSON object containing reply status, text, addressing and attachments. The old text protocols for commands, completion, progress, continuation and task budgets are no longer part of the model prompt; their strings are stripped only as a compatibility guard for stale threads.

Every model-handled turn—including private chat, an explicit mention or reply, a poke, and an approved proactive turn—retains a final no-reply choice through structured `status: "silent"`; the Hub records a `silent` lifecycle and sends nothing. Deterministic management slash commands still return their execution result. Any visible claim that a real QQ write action completed—including a poke, friend add, group join, request decision, moderation action, or QQ Space write—must follow the matching `qq_social.act` dynamic tool and an explicit successful result. The Bot may refuse before calling the tool, but it must report an action that already succeeded and must never claim success after failure. The Hub retains deterministic protection for a few legacy counter-poke phrases before delivery.

Codex defaults to two active child processes and 32 pending jobs. Each group or private scope has one complete reply lifecycle. While a reply is being generated, every later message that actually triggers the Bot—direct mention, reply to the Bot, interest-model approval, or another response rule—enters one fusion buffer. As long as the current answer is still generating, every new follow-up restarts a five-second quiet timer; after five continuous seconds without another follow-up, the Hub combines trigger messages, nearby context selected by the existing context policy, adjacent-repeat compaction, and images into one input. It then directly cuts the old turn with `turn/interrupt` and starts one replacement answer in the same thread with `turn/start`; it does not leave a stale draft alive behind a best-effort steer. If app-server reports that the old turn already became inactive during this boundary race, the Hub still starts the replacement turn instead of retaining the batch. If the replacement turn produces no app-server protocol activity for 60 seconds, the Hub stops that process early and retries once in a fresh app-server thread with the original complete prompt plus the accepted fused input; an ordinary non-fused timeout is never retried by this path. If the current answer finishes before the five-second quiet window ends, the Hub does not send that completed draft or wait for the remaining timer. It cancels the unfinished timer immediately, starts the next Codex turn with the fused follow-ups, and replaces the unsent draft; newer follow-ups repeat the same replacement rule until one unified answer reaches delivery without another pending batch. The Hub does not resend full context for every trigger. `/stop` interrupts only the current reply and clears its pending fusion queue while preserving rolling context, short-term notes, and the reusable Codex thread; `/新对话` additionally clears those conversation-scoped layers and cuts the thread mapping.

QQ replies support `temporary`, `persistent`, and `auto` Codex session modes. Temporary mode starts an isolated thread for each top-level reply. Persistent mode uses `thread/resume` for the current group or private scope, adds only unseen context, and excludes messages already present in the current trigger batch. Auto mode selects persistent after three replies in six hours, five replies in 24 hours, or when a thread was used within 72 hours; otherwise it selects temporary. All three modes share the same fused follow-up path. Owners can use `/会话模式 自动|长期|临时` for the current scope, and `/新对话` cuts the reusable thread mapping.

In group replies, visible text in the form `@exact member name ` or `@QQ-number ` is converted into a real OneBot `at` segment. The Hub resolves exact names from current/recent identities and a cached group-member list, prefers a QQ number when names collide, refuses ambiguous names, limits one bubble to eight explicit targets, and emits exactly one normal text space after every real mention. Explicit model-selected targets override the automatic sender-addressing mention for that bubble.

When one fused answer contains Bot-triggering messages from multiple people, the main model receives the exact participant list. The structured reply object can select `quote`, `mention`, `plain`, or `automatic` plus one listed QQ number. Missing or invalid targets fail closed to plain/automatic delivery, so an answer to a later participant cannot accidentally target the first trigger. Visible `@exact-name ` / `@QQ-number ` remains available for explicit or multiple mentions.

Delivery is receipt-aware. Successful bubbles alone enter the Bot's sent-message memory. Any failed bubble is stored separately as a bounded QQ delivery receipt, and the next model turn is told that the content did not reach QQ and must not be treated as something the other person already saw. Partial multi-bubble delivery records both the delivered and failed counts.

Codex deadlines are selected by task type instead of sharing one constant. Defaults are three minutes for ordinary replies, four minutes for vision replies, 90 seconds for context summaries, 90 seconds for self-persona work, five minutes for owner file tasks, and ten minutes for image generation. Each class has an independent environment override. Every accepted steered follow-up or fused replacement turn renews the full task-specific window, so a newly started answer does not inherit only the previous turn's remaining time. Runtime state and logs report the selected task type, deadline, and renewal count, while `/stop` can still terminate work early.

## Context and memory

| Layer | Content | Storage |
| --- | --- | --- |
| Rolling context | Recent human and Bot messages per scope | `data/qq-memory.json` |
| Conversation transcript | Bounded messages and image references since `/新对话` | Runtime state and local persistence |
| Codex session mapping | Thread, model, and last injected context position for auto/persistent scopes | `data/qq-codex-sessions.json` |
| Short-term memory | Current-scope temporary notes managed by `/记忆`; cleared by `/新对话` | `data/qq-memory.json` plus the shared semantic index |
| Social memory | Brief/detailed group impressions plus bounded cross-group person impressions keyed by QQ number | `data/qq-conversation-memory.json` plus the shared semantic index |
| Long-term knowledge base | Titled stable knowledge and slang scoped globally, by group, person or group-person | `data/qq-knowledge-base.json` plus the shared semantic index |
| Legacy public memory | Compatibility data imported once into the long-term knowledge base | `data/qq-public-memory.json` |
| Adaptive statistics | Group rhythm, structural style and interaction counts | `data/qq-personas.json` |
| Global self-persona | Privacy-filtered summaries from individual scopes | `data/qq-self-persona.json` |
| Unified memory | Shared recall across impressions, short-term items, knowledge and durable context | `data/semantic-memory.sqlite` plus source persistence |

`/stop` leaves rolling context, current-scope `/记忆` notes, and the reusable Codex thread intact; if a persistent thread has just started, its mapping is retained before interruption. `/新对话` clears rolling context, the current transcript, current-scope `/记忆` notes, and the Codex thread mapping, while social impressions and the long-term knowledge base survive. It stops reusing the old Codex thread but does not delete Codex CLI's local historical archive. Group impressions stay inside their group. The QQ number is the stable person key; group cards, group nicknames, private-chat names, and Bot-managed aliases all map to that key. Legacy impressions migrate into version 4 brief/detail and unified-person metadata; a later summary for the same stable profile ID replaces the migrated version in place. Legacy public memory is imported into the knowledge base.

Normal replies use one distance-aware context policy after adjacent-repeat compaction. Group triggers send the newest 20 model-visible messages in full, explicit @Bot/reply-to-Bot triggers send 30, and an expanded retry sends 48; private chat sends 30, or 60 when expanded. Only the older part of the retained rolling transcript is relevance-filtered. Its semantic query combines the current message, quoted message and any accepted fused follow-ups, and it may select both human messages and Bot replies together with bounded preceding context. A fused replacement reruns this distant-message search, excluding transcript fragments already injected into that turn.

Short-term memory, knowledge, impressions and unified memory share the same query and one local hybrid recall plane. SQLite stores versioned 1024-dimensional deterministic Chinese/English feature vectors with separate title, brief and detail weights, plus Chinese word/phrase, synonym concept, entity, version, time and polarity features. This is a local hashed feature model, not a BERT neural embedding. FTS5 supplies full-text candidates, then semantic coverage, lexical, title and recency signals are merged into the final rank. A model-version change automatically rebuilds old vectors from their source text. Runtimes without built-in SQLite safely fall back to an atomic JSON index. Original JSON stores remain the compatibility, audit and recovery sources; startup and each write project the affected layer into the semantic index.

Person recall identifies real senders, quoted/mentioned QQ ids, and known QQ numbers in text first. A textual name matches only when the merged group-card, group-name, private-name, and managed-alias set resolves to exactly one person. Every detected person contributes only a brief automatically. After reading the full profile, the main model may set `personImpressionComplete` when the profile is stable, non-sensitive, multi-dimensional, and mature; the Hub then promotes the stable QQ profile and per-session AI profile revisions into unified memory. Future recognition of that person in any group or private chat expands semantic recall to those other sessions, but exposes only AI-curated person memory rather than raw group chat or group-private facts. `/人物记忆 详细 QQ号` is advertised only for people detected in the current turn. The Bot can also list, add, remove, or replace aliases through `/人物别称`; removed names stay suppressed, while the QQ number remains authoritative.

`/记忆` follows the knowledge base's search-before-update policy. Every short-term item has a title, brief, detail and lifecycle status. A semantically similar add pauses for the main model to choose replace, stale/archive, or genuinely coexist. `/记忆 覆盖` preserves the stable ID, `/记忆 过时` immediately removes an item from recall while retaining audit detail, and `/记忆 详细` retrieves the full body.

Raw chat records remain stored message by message for frequency accounting, time-based reasoning, and audit. Compaction happens only while assembling model input. A semantically identical adjacent run is collapsed from two messages onward, keeping the last message as the current sender representative and appending `（连续重复 N 条）`. Separate runs are compacted independently, non-adjacent identical text is never merged, and differences in Bot/human role, mentions, quotes, or images prevent a merge. The same rule covers main-reply context, interest judgments, cold/private context, chat/persona summaries, the history tool, and knowledge-deletion evidence.

Conversation summaries no longer see only the cache collected since the current Hub process started. They page NapCat `get_group_msg_history` or `get_friend_msg_history` for up to 300 messages (600 when the command requests all), merge those records with Hub-local history by message ID, and report an explicit local-only fallback if the API fails. Summary, persona and style work remain separate model tasks with independent schedules. When schedules happen to overlap they reuse one short-lived history snapshot; otherwise each task runs independently.

Every knowledge entry requires a title. Slang stores a term and explanation with global, group, person or group-person variants; group name/number and person nickname/QQ number remain as scope identity. If the same person has the same interpretation in multiple groups, Hub promotes it to one cross-group person variant. When a message matches slang, only interpretations applicable to the current group and current speaker are shown to the reply and interest models. Hidden `/知识库` tools list titles, search or view a title, add ordinary knowledge or slang, and support current or owner-authorized cross-scope ranges.

Ordinary knowledge is not a fixed catalog. Each scope-summary pass receives the previous summary and topics as compressed evidence from older chat, then combines them with new messages to retain, revise, or remove topics; the everyday main model also receives the current scope summary as weak context. Knowledge selection therefore follows what that group actually discusses over time, evolves with its changing focus, and never assumes or permanently applies a predefined domain. Only reusable facts, references, experience, or agreements tied to those real topics are saved, so different groups naturally develop different knowledge. External changing knowledge uses a stable title without a date or version number, while its content records an as-of date, verification state, fact, and source; formatted entries expose their latest update time. On a relevant future turn, when old content may be stale or the user asks for the latest state, the tool-capable main model checks the old title, uses an already supplied web summary or searches, and overwrites the same title and scope. Conflicting sources are not promoted to a settled fact. Summary jobs without web tools may only label chat-derived claims as `conversation pending verification`; they cannot claim web verification. Internal group rules that cannot be checked publicly are labeled as group agreements or consensus.

Summary and impression updates receive existing in-scope knowledge. The same title and scope replace old content, and equivalent renames keep an alias, preventing append-only growth. Slang hits track counts and first/last timestamps and retain a bounded copy of each matching message with up to three messages before and after it. Old, persistently low-frequency slang creates a deletion application rather than being deleted directly. The interest model first sees statistics plus a small first/last sample for low-temperature triage and risk labels; the main model then reads all retained evidence and makes the final keep/delete decision. Failure in either stage keeps the entry. Any new hit or content change during review also keeps it. A malformed knowledge file is preserved and writes are blocked.

Recurring QQ behavior uses persisted wall-clock timestamps instead of process uptime. The scheduler checks immediately at Hub startup, again when the QQ channel is enabled, and then at the configured poll cadence. If the device or Hub was stopped past a due time, it performs one catch-up check; it never replays every missed interval in a burst. After a catch-up action completes, its next interval starts from completion time. Ordinary group-interest cycles persist their pending count, cycle start and bounded latest candidate in `data/qq-memory.json`; adaptive reviews, cold/private interest and self-persona summaries/generation use the timestamps in their existing persona stores. Manual `/总结聊天记录` and unified-memory read/write remain event-driven rather than being turned into artificial recurring jobs.

## Adaptive social behavior

- `qq-human-behavior` derives anonymous short-window message length, rate, bursts, media/emoji, reply/mention, question and punctuation signals without copying a member's wording. The main model receives the per-turn dynamic behavior plan without a second fixed "group chat style" block.
- `qq-adaptive-learning` persists activity, structure, interaction distance and post-Bot feedback to weakly tune length, sticker probability, bubble rhythm and delay. It also treats consecutive human messages no more than two minutes apart as active transitions and records the share whose sender changes as the group-level interjection rate.
- A persisted 24-hour review clock runs a separate main-model comparison of human and Bot openings, context handoff, sentence shape, explanatory tone, punctuation, emoji, questions, bubbles and service-like language. The UI stores a precise brief, full diagnosis and executable rules; each review replaces its previous version. Fixed statistical rules are only a failure fallback.
- The global self-persona is generated only from privacy-filtered scope summaries. Raw private content must not cross scopes.
- Adaptive data changes style and cadence; it never bypasses allowlists, permissions or the interest judge.

## Proactive interest

Three constrained paths exist:

1. **Ordinary group interest:** unmentioned messages enter a persisted per-group pending cycle. The first completed message or non-empty wall-clock minute threshold invokes the configured provider's semantic judge. Empty cycles do not call a model, and a restart immediately checks an overdue non-empty cycle. Once at least one Bot bubble is confirmed delivered to the group, every pending ordinary message from before that delivery is discarded and the next frequency cycle starts with later human messages; an old judge still in flight is superseded without consuming messages that arrived after the delivery. A cycle restored from disk bypasses the normal online stale-topic discard exactly for that catch-up judge, so a long shutdown cannot silently consume the overdue work; new activity during the judge can still supersede its result.
2. **Cold-group interest:** once learned activity, recent human/Bot traffic, unanswered output and activity windows make a quiet group eligible, the interest model returns `silent`, `topic`, or `chatter`. A decline or judge failure never starts the main model. `topic` lets the main model select from its own interests and optionally use multi-round Agent research; `chatter` authorizes rare lightweight presence. The interest model never supplies a concrete topic, query, reply draft, or chat style.
3. **Private interest:** interaction frequency, time since activity and unanswered Bot output first produce a frequency prior and human-like variation roll. The interest model then makes the final start decision. A decline or failure does not launch the main model; after approval, the main model writes the message without re-deciding whether to contact the person.

The ordinary group judge uses a streaming compatible request: OpenRouter gets strict JSON Schema, while DeepSeek and custom OpenAI-compatible providers use JSON Object mode. The validated ordinary result contains only `shouldReply`, `interest`, and `reason`; it no longer emits an analysis trace, semantic summary, reply draft, or style advice. Cold/private start gates additionally normalize only unambiguous JSON-mode drift—fractional, boolean, or low/medium/high interest values and an omitted diagnostic reason—while the boolean start switch and allowed modes remain strict. This prevents a valid start decision from being discarded merely because a JSON Object provider shaped its score differently. The approved main model reads the original message, quote, and recent context directly. Ordinary group judgment uses temperature `0.65`, cold/private gates use `0.8`, and complex-deletion triage uses `0.15`. Invalid decisions get at most one retry; timeouts, HTTP failures, and rate limits are not blindly retried.

The interest model is the lightweight background-decision and miscellaneous-triage plane. Ordinary proactive gates, cold/private starts, short classification, risk labels, and the first bounded pass of a complex task use the same configured channel. It never writes user-facing chat and does not own conversation summaries, group/person impressions, persona summaries, or knowledge extraction. The main model owns conversation, summaries, and complex work: final replies, contextual understanding, tool research, topic expression, every summary/knowledge extraction task, and the final handling of long-context or multi-evidence work.

The interest judge receives the learned group interjection rate, its active-transition sample count and the measurement window. These are timing references only: a high rate never triggers a reply by itself, and a low rate is not a hard silence rule. The structured model decision and interest threshold remain authoritative.

Proactive work does not force itself behind active generation. New activity suppresses stale results. Ordinary interjection, cold autonomous topic, cold lightweight chatter, and private outreach all carry one enforced `interest gate -> main content` contract; Hub blocks sending if either stage is missing. The main prompt is organized as role, interpretation order, response method, memory, safety, the one dynamic style plan, and the current task; approval appears only once. Common research tools stay visible while unrelated social operations are shown only when the current message makes them relevant. Detailed logs retain the two-model contract, cold/private judgments, temperature, bounded model outputs, cold exploration rounds, tool kinds, queries, failures, and final delivery outcome.

## Images, files, stickers and bubbles

- QQ images, screenshots, quoted images, share cards and bounded forwarded images can enter context. Direct current/quoted images are always eligible, while persisted incidental context images older than two hours (or missing a timestamp) are excluded before download so expired Tencent URLs do not turn an unrelated text reply into a failing vision request.
- Explicit drawing/generation requests and reference-edit wording such as edit, modify, replace the background, add/remove an element, change the style, or draw another image from this reference take the image-task path instead of the ordinary vision path. When the current or quoted message contains an image, a short instruction such as “change the background to blue” also passes that image to the drawing model as a reference; a plain “look at this image” remains a vision reply.
- The model can request local delivery through `[[qq_image:...]]`, `[[qq_file:...]]` and `[[qq_sticker:...]]`. Sticker delivery is selectable per reply: combine text and sticker in one QQ message, send only the sticker, or place the standalone multi-bubble separator between text and the sticker marker to send them as two ordered messages.
- File/image tasks use `runtime/qq-task-workspaces/<request>/input|output`. Only real paths inside the current request's `output/` pass delivery validation, preventing arbitrary file disclosure and symlink escapes.
- Local stickers, QQ account favorites and downloaded metadata form a bounded catalog. Animated items support bounded frame inspection, with labels stored separately.
- Sticker-favorite judgment runs only inside an already-triggered lifecycle; an ordinary untriggered sticker does not call a model by itself.
- A standalone `|||` splits consecutive bubbles. For separate sticker delivery, the text bubble is sent first and the sticker-only bubble follows as its own message. Separator, count and delay are configurable, and adaptation changes rhythm only for suitable social replies.

## Commands, permissions and social tools

Common public commands include `/菜单`, `/新对话`, `/stop` and `/总结聊天记录`.

Owners and Bot administrators can use `/会话模式` to inspect the current scope's configured/effective mode and auto counters, then `/会话模式 自动|长期|临时` to change it.

Privileged capabilities include status/configuration, model and reasoning selection, proactive policy, group allowlists, bans, command permissions, moderation, request handling and notifications. When the local NapCat social extension supports them, privileged tools can also initiate friend/group requests and perform QQ Space reads or writes. Active friend-add tools accept the canonical `/主动加好友` command plus the `/加好友` and `/添加好友` aliases. Stranger UID lookup and verification preflight are optional and time-bounded: failure or timeout never blocks forced submission by QQ number, and loopback-only `/inspect-friend` diagnoses a target without sending. The bridge may use `AddBuddyService` for read-only verification preflight, but it prefers the stable `BuddyService.reqToAddFriends(UIN, message)` path for submission and uses `AddBuddyService.addBuddy` only when that UIN API is unavailable. Explicit one-object native signatures remain supported, while hidden signatures start with the current two-argument UIN form and retry only after an explicit one-argument assertion, so other failures cannot duplicate a request. Native submission and Hub-to-bridge HTTP calls have deadlines; a stuck QQ API now returns an actionable timeout instead of leaving the conversation unanswered. A `submitted` result does not mean the peer accepted the request. QQ Space publishing supports `/发动态 text`, `/发动态 图片=当前`, and `/发动态 text | 图片=当前`, with up to nine current/quoted images copied into the task workspace; arbitrary server paths are rejected. Comment requests use the current topic-ID and charset fields.

The owner manages the persisted role with `/Bot管理员 添加 QQ_ID` and `/Bot管理员 删除 QQ_ID`. Bot administrators receive the full menu, native Agent, runtime/social tools and cross-session access, but cannot grant/revoke administrators and are never represented as owners. Their file Agent may normally read/create/modify project and task-workspace files, but must judge and refuse deletion of important files, critical source/config/data/credential overwrites, damage to `.git`, dependencies or runtime state, and ambiguous or unrecoverable destructive operations, including indirect bypass requests.

`/跨会话 列表 [filter]` lists known groups, private sessions and QQ identities already observed in allowed conversations, `/跨会话 查看 group:GROUP_ID 最近30` reads a target, and `/跨会话 发送 private:QQ_ID | text` performs a real QQ send. A known participant can therefore be selected before a private exchange exists; the catalog labels that target as having no private history. Native `qq_session.manage` can select one target so later compatible history, memory, knowledge and QQ tools in the same Agent turn operate there until focus is changed or cleared. Stable `group:` / `private:` selectors avoid ambiguous bare numbers. A send requires an explicit owner/administrator request and is written into target history only after confirmed delivery.

Ordinary-user menu visibility and execution come from the same permission keys. Owner IDs, Bot administrators and the Bot itself cannot be demoted, banned, muted or kicked by ordinary users. Separately, the main-model system prompt fixes QQ `3784642920` as this project's developer; that project identity is not derived from, and does not change with, the current owner list. Owner/administrator authority still comes only from trusted Hub event identity.

## Web lookup

The Hub performs QQ web lookup independently of this chat interface. Configured provider order can include Tavily, Bing, Baidu, 360, Sogou and DuckDuckGo, with `balanced`, `china`, `global`, `tavily` and `privacy` presets. Results remain untrusted material and cannot override sender permissions or system policy.

Inspect the effective provider, attempts and recent errors through `/api/maintenance` and `search` logs.

## Dashboard, API and logs

The local dashboard exposes service/channel state, allowlists, models, short-term memory, adaptive learning, proactive interest, maintenance, structured log filters, language, theme and responsive layouts. Its dedicated long-term Knowledge workspace filters slang or notes by global, group, member, or group-member scope; it shows same-title scoped meanings, hit frequency, recent chat context and model-review outcomes, and can precisely create, edit or delete the selected scope. Its persistent LAN switch creates a management token; the token can only be retrieved from a loopback-loaded dashboard. A separate, default-off Cloudflare Quick Tunnel switch can create a temporary HTTPS address without rebinding the Hub away from loopback. Remote management APIs still require the same token, while tunnel start/stop and token-copy controls remain local-only.

Automatic polling keeps server-backed readouts current without overwriting a control that is being changed or unsaved Bot settings. The current browser tab keeps Bot-setting drafts, the group-ID draft, short-term-memory tab/search/expanded groups, knowledge filters/selection, and log filters/pause/follow/scroll context in session storage, then restores them after a full page reload. Knowledge edits use both entry and variant IDs for stale-write protection, and deletion affects only the selected scope. The returned server state remains authoritative after a successful mutation.

Core read endpoints:

```text
GET /api/state
GET /api/maintenance
GET /api/logs
GET /api/memory
POST /api/qq/knowledge
```

JSONL schema v3 remains backward-readable. Agent turns/tools, cross-session sends, friend/group additions, administrator changes and settings persistence share `operation`, `outcome`, actor role/ID, source/target scope/type, tool identity, duration and error-code fields; dynamic-tool arguments and cross-session message bodies are not logged. The API and `ncc logs` add `scope` and `operation` filters to level, category, trace, group, sender, query, time and latency, while summaries count operations and outcomes. A QQ lifecycle shares one trace from inbound routing through judging, follow-up fusion, search, Codex and delivery. Fusion events report the five-second buffer, direct interrupt-and-replacement, completed-draft replacement before delivery, trigger sources, raw/compacted counts, selected in-between context, images, and a bounded preview. Delivery records include delivered/failed bubble counts, and a failed receipt is logged when it is retained for the next model turn. `ncc logs` renders these events with the existing colored severity/category captions and Chinese detail labels. Short-term memory changes, knowledge queries/updates, slang frequency hits, low-frequency deletion applications and model reviews all use the same structured `memory` category. Concrete Codex and interest-model output is retained as bounded, secret-redacted `debug` detail without copying the full input prompt; the Chinese terminal and browser logs recursively localize startup adaptive-learning snapshots and other detail fields.

## macOS client

The native macOS client is a WebKit wrapper around the same local dashboard and QQ/OneBot Hub used by the browser. It does not read the Messages database, poll iMessage, require Messages Automation and Full Disk Access, or expose macOS-only proxy, display, keep-awake or desktop-control features.

## Explicit boundaries

- This is not the official QQ Bot OpenAPI or a hosted public Bot service.
- QQ, NapCat and LLBot installers are not included.
- QQ risk controls, QR login, verification and OS permissions are not bypassed.
- LAN/public access and unauthenticated remote management are disabled by default.
- Adaptive behavior must not imitate or expose a specific member's private wording or facts.
