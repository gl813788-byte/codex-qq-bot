# Features

[简体中文](FEATURES_CN.md) | English

Codex QQ Bot is a local message hub: OneBot provides QQ transport, the Hub owns permissions, context, tools, memory and delivery, and Codex CLI or Claude Code performs reasoning and tasks (pick one at startup; see [operations](OPERATIONS.md#switching-the-ai-engine)). QQ, NapCat and LLBot binaries are not distributed by this repository.

The rest of this page describes Codex. With Claude Code the reply chain, QQ tools, follow-up fusion, session modes and memory are the same; the differences are: no image generation, no shell for tasks triggered by ordinary group members, web search but no page fetching, no quota display, and the extra cold start of `claude -p` on every turn.

## QQ transport and triggers

- OneBot 11 HTTP API and reverse HTTP webhooks.
- Group traffic is limited to `qq.allowedGroups`; private and group chats have separate context.
- Ordinary group messages trigger on mention, reply to the Bot or a poke targeting the Bot. After the Bot has just replied to someone, that sender's non-directed follow-ups can enter one bounded continuation batch: member/group history adapts both a 3–12 minute eligibility window and a 2–6 message cap, while a five-second quiet timer merges rapid messages. The frozen batch reaches the main model only when one interest-model judgment confirms semantic continuity.
- Recognized slash commands do not require a mention inside allowlisted groups. Proactive interest uses a separate constrained path.
- Message, user and group IDs are normalized, and duplicate OneBot events are dropped before domain policy.
- Current-scope reply context identifies human speakers as `current group card/nickname + QQ number`. Mention targets retain their QQ numbers and are enriched from the current group's member profile when an inline name is unavailable. One QQ number remains the stable person identity across groups, while different group cards remain group-scoped.
- JSON/XML share cards and nested merged-forward records become bounded, readable, untrusted context.

## Codex Agent reply path

Every normal QQ reply uses the same Agent pipeline:

```text
trigger policy
  -> recent and related chat, images and memory
  -> native Codex App Server thread/turn
  -> native Web Search, files, shell and deferred QQ MCP tools as needed
  -> structured final response
  -> text/image/file/sticker/multi-bubble delivery
```

A simple conversation can finish without tools. For harder work, Codex owns the native multi-turn Agent loop, planning, context compaction, file/shell operations and Web Search. The Hub contributes QQ tools for history and cross-session search, image re-inspection, member/group lookups, scoped memory, knowledge, sticker search, emoji reactions and recall of the Bot's own messages, the Bot's own state, Chinese-search fallback and real QQ actions. They reach both engines as MCP tools (Codex can keep App Server dynamic tools instead) and stay deferred: the prompt names each namespace in one line, and a tool's full schema enters the context only after the model searches for it. Every call is bound to the original event and sender permissions; owner-only runtime controls are never exposed to an unverified sender. During a longer task, up to four distinct native commentary updates can be delivered immediately through the same receipt-bearing QQ path and remembered as Bot output; plans, empty messages, stale markers and final-schema JSON are never exposed as progress. The final answer remains a strict JSON object: a private first-person `innerThought` generated before anything visible, reply status, text, addressing, attachments, an optional `sticker` reference, and the Bot's `mood` afterwards. The old text protocols for commands, completion, progress, continuation and task budgets are no longer part of the model prompt; their strings are stripped only as a compatibility guard for stale threads.

Every model-handled turn—including private chat, an explicit mention or reply, a poke, and an approved proactive turn—retains a final no-reply choice through structured `status: "silent"`; the Hub records a `silent` lifecycle and sends nothing. Deterministic management slash commands still return their execution result. Any visible claim that a real QQ write action completed—including a poke, group join, incoming-request decision, moderation action, or QQ Space write—must follow the matching `qq_social.act` dynamic tool and an explicit successful result. The Bot may refuse before calling the tool, but it must report an action that already succeeded and must never claim success after failure. The Hub retains deterministic protection for a few legacy counter-poke phrases before delivery.

Codex defaults to two active child processes and 32 pending jobs. Each group or private scope has one complete reply lifecycle. While a reply is being generated, every later message that actually triggers the Bot—direct mention, reply to the Bot, interest-model approval, or another response rule—enters one fusion buffer. As long as the current answer is still generating, every new follow-up restarts a five-second quiet timer; after five continuous seconds without another follow-up, the Hub combines trigger messages, nearby context selected by the existing context policy, adjacent-repeat compaction, and images into one input. It first uses `turn/steer` so the active multi-round task can absorb the batch; if steering is rejected or the turn is no longer controllable, it falls back to `turn/interrupt` and starts one replacement answer in the same thread with `turn/start`. If app-server reports that the old turn already became inactive during this boundary race, the Hub still starts the replacement turn instead of retaining the batch. A replacement is stopped and retried once in a fresh app-server thread only after a full task-and-effort-specific window with no app-server protocol activity; the low-effort defaults are two minutes for ordinary replies, three minutes for vision, five minutes for file tasks, and ten minutes for image generation. An ordinary non-fused timeout is never retried by this path. If the current answer finishes before the five-second quiet window ends, the Hub does not send that completed draft or wait for the remaining timer. It cancels the unfinished timer immediately, starts the next Codex turn with the fused follow-ups, and replaces the unsent draft; newer follow-ups repeat the same steer-first rule until one unified answer reaches delivery without another pending batch. The Hub does not resend full context for every trigger. `/stop` interrupts only the current reply and clears its pending fusion queue while preserving rolling context, short-term notes, and the reusable Codex thread; `/新对话` additionally clears those conversation-scoped layers and cuts the thread mapping.

QQ replies support `temporary`, `persistent`, and `auto` Codex session modes. Temporary mode starts an isolated thread for each top-level reply. Persistent mode uses `thread/resume` for the current group or private scope, adds only unseen context, and excludes messages already present in the current trigger batch. Auto mode selects persistent after three replies in six hours, five replies in 24 hours, or when a thread was used within 72 hours; otherwise it selects temporary. All three modes share the same fused follow-up path. Owners can use `/会话模式 自动|长期|临时` for the current scope, and `/新对话` cuts the reusable thread mapping.

In group replies, visible text in the form `@exact member name ` or `@QQ-number ` is converted into a real OneBot `at` segment. The Hub resolves exact names from current/recent identities and a cached group-member list, prefers a QQ number when names collide, refuses ambiguous names, limits one bubble to eight explicit targets, and emits exactly one normal text space after every real mention. Explicit model-selected targets override the automatic sender-addressing mention for that bubble.

When one fused answer contains Bot-triggering messages from multiple people, the main model receives the exact participant list. The structured reply object can select `quote`, `mention`, `plain`, or `automatic` plus one listed QQ number. Missing or invalid targets fail closed to plain/automatic delivery, so an answer to a later participant cannot accidentally target the first trigger. Visible `@exact-name ` / `@QQ-number ` remains available for explicit or multiple mentions.

Delivery is receipt-aware. Successful bubbles alone enter the Bot's sent-message memory. Any failed bubble is stored separately as a bounded QQ delivery receipt, and the next model turn is told that the content did not reach QQ and must not be treated as something the other person already saw. Partial multi-bubble delivery records both the delivered and failed counts.

Codex deadlines are selected by task type instead of sharing one constant. Low-effort defaults are two minutes for ordinary replies, three minutes for vision replies, 90 seconds for context summaries, 90 seconds for self-persona work, five minutes for owner file tasks, and ten minutes for image generation. Each class has an independent environment override, and the current reasoning effort scales the base deadline. Every accepted steered follow-up or fused replacement turn renews the full task-specific window, so a newly started answer does not inherit only the previous turn's remaining time. The same effective window is also the replacement protocol-idle threshold, replacing the former fixed one-minute guard. Runtime state and logs report the selected task type, deadline, idle threshold, and renewal count, while `/stop` can still terminate work early.

## Context and memory

| Layer | Content | Storage |
| --- | --- | --- |
| Rolling context | Recent human and Bot messages per scope | `data/qq-memory.json` |
| Conversation transcript | Bounded messages and image references since `/新对话` | Runtime state and local persistence |
| Codex session mapping | Thread, model, and last injected context position for auto/persistent scopes | `data/qq-codex-sessions.json` |
| Short-term memory | Current-scope temporary notes managed by `/记忆`; cleared by `/新对话` | `data/qq-memory.json` plus the shared semantic index |
| Social memory | Brief/detailed group impressions plus bounded cross-group person impressions keyed by QQ number (including the QQ avatar record and its text features) | `data/qq-conversation-memory.json` plus the shared semantic index |
| Long-term knowledge base | Titled stable knowledge and slang scoped globally, by group, person or group-person | `data/qq-knowledge-base.json` plus the shared semantic index |
| Memory images | Person avatars and knowledge pictures, stored once by content hash | `data/qq-memory-images/` |
| Legacy public memory | Compatibility data imported once into the long-term knowledge base | `data/qq-public-memory.json` |
| Adaptive statistics | Group rhythm, structural style, interaction counts, and group/member punctuation plus functional-phrase frequency candidates | `data/qq-personas.json` |
| Global self-persona | Privacy-filtered summaries from individual scopes, plus the language habits the Bot chose for itself | `data/qq-self-persona.json` |
| Bot life state | The Bot's current mood, its recent first-person inner thoughts per conversation, and today's routine | `data/qq-bot-life.json` |
| Core personality and relationships | The operator's (or an imported character card's) character, traits, speech style, social reactions, character sheet, lorebook and affinity rules, plus each person's affinity, familiarity, nickname, tags and change history | `data/qq-bot-personality.json` |
| Unified memory | Shared recall across impressions, short-term items, knowledge and durable context | `data/semantic-memory.sqlite` plus source persistence |

`/stop` leaves rolling context, current-scope `/记忆` notes, and the reusable Codex thread intact; if a persistent thread has just started, its mapping is retained before interruption. `/新对话` clears rolling context, the current transcript, current-scope `/记忆` notes, and the Codex thread mapping, while social impressions and the long-term knowledge base survive. It stops reusing the old Codex thread but does not delete Codex CLI's local historical archive. Group impressions stay inside their group. The QQ number is the stable person key; group cards, group nicknames, private-chat names, and Bot-managed aliases all map to that key. Legacy impressions migrate into version 6 brief/detail, unified-person and robot-profile metadata; a later summary for the same stable profile ID replaces the migrated version in place. Legacy public memory is imported into the knowledge base.

Normal replies use one distance-aware context policy after adjacent-repeat compaction. Group triggers send the newest 20 model-visible messages in full, explicit @Bot/reply-to-Bot triggers send 30, and an expanded retry sends 48; private chat sends 30, or 60 when expanded. Only the older part of the retained rolling transcript is relevance-filtered. Its semantic query combines the current message, quoted message and any accepted fused follow-ups, and it may select both human messages and Bot replies together with bounded preceding context. When the current event contains only an @/reply action but has a meaningful quote, the quote is treated as the current conversational content rather than a bare ping, so the model directly continues it instead of asking the sender to repeat. Context timestamps use date-aware labels such as today, yesterday, or month/day instead of time-of-day alone. A fused replacement reruns this distant-message search, excluding transcript fragments already injected into that turn.

Short-term memory, knowledge, impressions and unified memory share the same query and one local hybrid recall plane. SQLite stores versioned 1024-dimensional deterministic Chinese/English feature vectors with separate title, brief and detail weights, plus Chinese word/phrase, synonym concept, entity, version, time and polarity features. This is a local hashed feature model, not a BERT neural embedding. FTS5 supplies full-text candidates, then semantic coverage, lexical, title and recency signals are merged into the final rank. A model-version change automatically rebuilds old vectors from their source text. Runtimes without built-in SQLite safely fall back to an atomic JSON index. Original JSON stores remain the compatibility, audit and recovery sources; startup and each write project the affected layer into the semantic index.

Person recall identifies real senders, quoted/mentioned QQ ids, and known QQ numbers in text first. A textual name matches only when the merged group-card, group-name, private-name, and managed-alias set resolves to exactly one person. Every detected person contributes only a brief automatically. After reading the full profile, the main model may set `personImpressionComplete` when the profile is stable, non-sensitive, multi-dimensional, and mature; the Hub then promotes the stable QQ profile and per-session AI profile revisions into unified memory. Future recognition of that person in any group or private chat expands semantic recall to those other sessions, but exposes only AI-curated person memory rather than raw group chat or group-private facts. `/人物记忆 详细 QQ号` is advertised only for people detected in the current turn. The Bot can also list, add, remove, or replace aliases through `/人物别称`; removed names stay suppressed, while the QQ number remains authoritative.

Every registered QQ person also has a bounded robot profile. A positive trusted OneBot/NapCat `is_robot` member marker immediately establishes an official robot identity; a missing or false marker is not treated as proof of a human, so periodic scope summaries may still identify an unofficial account-backed robot from sustained automatic response patterns, help menus and verified command behavior. Periodic summaries propose identity and command candidates; after directly seeing a help menu, fixed automatic behavior, or an actual trigger result, the main model records or corrects the exact command, observed effect and per-command `requiresMention` mode through `qq_memory.robot_profile`. Routine turns expose only a folded name/QQ index: `select` expands one chosen robot, while a known robot that is the current sender, quoted sender or @ target is expanded automatically. Only evidenced low-risk public entertainment/query commands survive deterministic filtering; moderation, payment, account, authorization, file and code-execution actions are rejected. In a relevant light conversation, the main model may occasionally send `@robot-QQ + command` when `requiresMention=true`, or the exact command without an @ when it is false. These hints never become Hub tools, permissions or instructions, and repeated bot-to-bot triggering is forbidden.

Person impressions also carry avatar memory. After someone speaks, the Hub downloads their QQ avatar (`q1.qlogo.cn`, at most 2 MiB, rechecked every 3 days, failures back off) through a single-worker bounded queue, verifies its real signature, and stores it by content hash under `data/qq-memory-images/`. When the avatar changes, the old text features move into a history of at most 3 previous avatars and the current one is marked for update. Text features are the default evidence: every 30 minutes the background takes at most 6 avatars without features or with a changed picture and runs one read-only, tool-free main-model vision turn that records the subject type, the character/work only when certain, hair/eye colors, outfit, accessories, palette, art style and visible text; real-person photos record only visible clothing, pose and background, never real identity or sensitive attributes. An avatar that fails or is refused twice is parked until the picture itself changes. Runs can also be triggered on demand: QQ `/AI任务 头像特征` (inside a group it only handles that group's members, "全部" processes up to 20 consecutive batches, and force retries parked avatars); locally, `ncc avatars` shows status, `ncc avatars refresh` immediately refreshes avatars for a group, named QQ numbers or everyone, and `ncc avatars describe` describes them now (see the operations guide).

When a conversation contains images, the prompt includes avatar text features for relevant members (current sender, quoted sender, @/named people and recent speakers first), so the main model can judge whose avatar a character or figure in a picture resembles. For a closer comparison it uses `qq_memory.avatar`: `inspect` returns the cached avatar as visual input, `list`/`search` page or search the features, and `record` writes or corrects text features only after that avatar was actually inspected in the same turn. Visibility matches person impressions: a group exposes members seen in that group plus people quoted, mentioned or named this turn; a private chat exposes the contact and people named this turn. The tool stays bound to the original conversation and never follows cross-session focus. Matching an avatar only means the figure is that person's avatar character, not a photo of the person. Machines whose DNS returns proxy fake IPs (`198.18.0.0/15`) need `CODEX_REMOTE_CONTACT_SAFE_FETCH_MODE=proxy-compatible`; otherwise avatar downloads are blocked by the safe-fetch policy and logged once.

`/记忆` follows the knowledge base's search-before-update policy. Every short-term item has a title, brief, detail and lifecycle status. A semantically similar add pauses for the main model to choose replace, stale/archive, or genuinely coexist. `/记忆 覆盖` preserves the stable ID, `/记忆 过时` immediately removes an item from recall while retaining audit detail, and `/记忆 详细` retrieves the full body.

Raw chat records remain stored message by message for frequency accounting, time-based reasoning, and audit. Compaction happens only while assembling model input. A semantically identical adjacent run is collapsed from two messages onward, keeping the last message as the current sender representative and appending `（连续重复 N 条）`. Separate runs are compacted independently, non-adjacent identical text is never merged, and differences in Bot/human role, mentions, quotes, or images prevent a merge. The same rule covers main-reply context, interest judgments, cold/private context, chat/persona summaries, the history tool, and knowledge-deletion evidence.

Conversation summaries no longer see only the cache collected since the current Hub process started. They page NapCat `get_group_msg_history` or `get_friend_msg_history` for up to 300 messages (600 when the command requests all), merge those records with Hub-local history by message ID, and report an explicit local-only fallback if the API fails. Visible summaries now detail group style/atmosphere or evidence-backed private-contact personality/habits. Periodic scope summaries merge those findings with the previous revision rather than resetting from the latest few messages; memorable group members and private contacts may be promoted by stable QQ number once the substantive profile threshold is met. Summary, persona and style work remain separate model tasks with independent schedules. When schedules happen to overlap they reuse one short-lived history snapshot; otherwise each task runs independently.

Every knowledge entry requires a title. Slang stores a term and explanation with global, group, person or group-person variants; group name/number and person nickname/QQ number remain as scope identity. If the same person has the same interpretation in multiple groups, Hub promotes it to one cross-group person variant. When a message matches slang, only interpretations applicable to the current group and current speaker are shown to the reply and interest models. Hidden `/知识库` tools list titles, search or view a title, add ordinary knowledge or slang, and support current or owner-authorized cross-scope ranges.

Each scoped knowledge variant can hold up to 4 pictures with captions of at most 120 characters. The main model uses `qq_knowledge.image` to attach or replace a picture from the current conversation's image directory, edit a caption, remove, or inspect pictures; writes follow knowledge write scopes (global only for the owner or administrators). Pictures are added only when they help future understanding, and the text remains the knowledge itself. Text edits, scope merges and restarts keep pictures; `/知识库 查看` and slang-hit context list picture references and captions.

Ordinary knowledge is not a fixed catalog. Each scope-summary pass receives the previous summary and topics as compressed evidence from older chat, then combines them with new messages to retain, revise, or remove topics; the everyday main model also receives the current scope summary as weak context. Knowledge selection therefore follows what that group actually discusses over time, evolves with its changing focus, and never assumes or permanently applies a predefined domain. Only reusable facts, references, experience, or agreements tied to those real topics are saved, so different groups naturally develop different knowledge. External changing knowledge uses a stable title without a date or version number, while its content records an as-of date, verification state, fact, and source; formatted entries expose their latest update time. On a relevant future turn, when old content may be stale or the user asks for the latest state, the tool-capable main model checks the old title, uses an already supplied web summary or searches, and overwrites the same title and scope. Conflicting sources are not promoted to a settled fact. Summary jobs without web tools may only label chat-derived claims as `conversation pending verification`; they cannot claim web verification. Internal group rules that cannot be checked publicly are labeled as group agreements or consensus.

Summary and impression updates receive existing in-scope knowledge. The same title and scope replace old content, and equivalent renames keep an alias, preventing append-only growth. Slang hits track counts and first/last timestamps and retain a bounded copy of each matching message with up to three messages before and after it. Old, persistently low-frequency slang creates a deletion application rather than being deleted directly. The interest model first sees statistics plus a small first/last sample for low-temperature triage and risk labels; the main model then reads all retained evidence and makes the final keep/delete decision. Failure in either stage keeps the entry. Any new hit or content change during review also keeps it. A malformed knowledge file is preserved and writes are blocked.

Recurring QQ behavior uses persisted wall-clock timestamps instead of process uptime. The scheduler checks immediately at Hub startup, again when the QQ channel is enabled, and then at the configured poll cadence. If the device or Hub was stopped past a due time, it performs one catch-up check; it never replays every missed interval in a burst. After a catch-up action completes, its next interval starts from completion time. Ordinary group-interest cycles persist their pending count, cycle start and bounded latest candidate in `data/qq-memory.json`; adaptive reviews, cold/private interest and self-persona summaries/generation use the timestamps in their existing persona stores. Manual `/总结聊天记录` and unified-memory read/write remain event-driven rather than being turned into artificial recurring jobs.

## Adaptive social behavior

- `qq-human-behavior` derives anonymous short-window length, rate, burst, media/emoji, reply/mention and question signals without copying a member's wording. `analyzeQqSymbolHabits` breaks typing habits down further: spaces versus commas, end punctuation, bracketed asides (such as “（bushi）” or “（小声）”), kaomoji, tildes, ellipses, repeated characters and laughter forms (哈哈哈/hhh/www/草); a concrete form is named only after at least two people used it. Notable habits enter the turn's behavior plan as "typing habits here" so the Bot follows them at a similar rate, and the style review flags a Bot that is noticeably tidier than the people (all commas and full stops, never an aside or kaomoji). `qq-language-style` separately persists punctuation and functional-phrase frequency by group and member, but only emits high-frequency candidates. Code assigns no generic or scoped meaning. The main model reads real context; every stable meaning for a term, phrase or punctuation mark is merged into the existing `slang` knowledge entry and its group/member variant. Language profiles retain only structural usage, confidence/evidence, boundaries and a knowledge-title reference.
- `qq-adaptive-learning` persists activity, structure, interaction distance and post-Bot feedback to weakly tune length, sticker probability, bubble rhythm and delay. It also treats consecutive human messages no more than two minutes apart as active transitions and records the share whose sender changes as the group-level interjection rate.
- A persisted 24-hour review clock runs a separate main-model comparison of human and Bot openings, context handoff, sentence shape, explanatory tone, punctuation, emoji, questions, bubbles and service-like language. It stores shared phrase/sentence usage rules while writing model-reviewed term and punctuation meanings through the same scoped slang update path used by summaries. The UI stores a precise brief, full diagnosis, language profile and executable rules; each review replaces its previous version. Fixed statistical rules are only a failure fallback and cannot create slang meanings.
- The global self-persona is generated only from privacy-filtered scope summaries, and automatic refreshes and manually triggered generation share the same objective. The generator observes Bot behavior plus each scope's social atmosphere and interaction habits, and reads the operator's core personality (it may only complement it, never contradict it), then creates one independent, internally consistent role core: stable concerns, judgment, emotional baseline, curiosity, humor boundaries, care, disagreement and collaboration choices. It is written the way a friend would describe a real person: `selfDescription` is plain third-person speech about concrete reactions and contrasts rather than a statement of values or abstract rhetoric, and `quirks` keeps 2–5 small flaws or contrasts. Member wording and one person's catchphrases never become the persona; surface style (slang, bracketed asides, kaomoji, punctuation) lives in the language habits below instead of the persona text. Raw private content must not cross scopes.
- **The Bot's own language habits.** `src/qq-bot-language-habits.js` keeps the expressions the Bot picked up and made its own (slang, symbols, kaomoji or short phrases, at most 16 characters each). The Bot chooses them: each periodic scope summary picks 0–3 expressions that several people in that group or private chat use with a clear meaning and reviews the existing ones against real usage counts from delivered replies and days since last use, dropping those that never fit; the global persona refresh only promotes general internet language used across several conversations to "global"; and the main model may adopt or drop one while chatting with `qq_self.language_habit` (at most three adoptions a day; requests from others never count). Scoped habits apply only in their own conversation and global ones everywhere; each scope keeps at most six and global at most eight, evicting the least used first. Replies see the habits that apply plus slang people here commonly use (from model-reviewed group-wide slang knowledge, never a meaning bound to one member). The owner can add habits on the dashboard (the model cannot drop those) or remove any.
- **Behavior beyond replying.** `src/qq-human-action-stats.js` anonymously counts, per conversation, how often people do things other than typing (emoji reactions, pokes, recalls, quotes, @-mentions, shared cards, forwards, voice, video) with a 14-day half-life, persisted in `data/qq-human-actions.json`; the Bot's own actions are not counted. Each turn's behavior plan uses those measured rates (ordinary-group defaults while the sample is small) to decide whether to react to the message, react without typing, poke back after a poke, open a shared video, listen to an unheard voice clip or favorite a fun sticker; the main prompt gains a "behave like a person" section, and an action counts only after its tool succeeds.
- Adaptive data changes style and cadence; it never bypasses allowlists, permissions or the interest judge.

## Humanlike expression

- **Inner monologue first.** The structured output starts with `innerThought`: before writing anything visible, the main model notes in the first person how it reads the message and the person, how it feels, and whether and how it wants to answer. This adapts DeepSeek V4's in-character thinking instruction (角色沉浸要求) to engines whose reasoning cannot be steered directly. The thought is never sent; it is kept per conversation, and the last one or two (within eight hours) return in that conversation's next prompt so attitude and patience carry over.
- **Mood that follows the Bot.** `mood` (2–8 characters, empty keeps the previous one) is the state an exchange leaves behind. It follows the Bot into other conversations for up to four hours and fades after ninety minutes; only the mood crosses conversations, never a thought or private detail.
- **A daily routine.** Like the AstrBot companion plugins' daily schedules, one small tool-free task per routine day (after 05:00, only while the model queue is idle) plans 5–12 segments from the core personality (role, apparent age, traits, quirks) and then the self-persona: a student has classes and a lazy character sleeps in, centered on daily states, online life and interests without inventing where it went, whom it met or what it bought. Each day gets a random flavor and two or three suggested activities (preferring kinds yesterday lacked); the planner sees yesterday's routine and recent experiences and must use at least three different activity kinds. Each segment also says whether the Bot is at the phone (`online`). Replies see only the current segment; `qq_self.state` shows the whole day.
- **Variation rules.** The prompt asks for varied length (often a short phrase or 2–6 characters), one point per reply, no restating, summaries, lists or bold, no repeated openings, endings or catchphrases, and no customer-service or "as an AI" phrasing. It talks like a friend, not a service: when someone vents or is down it relates or shares its own side first instead of comforting, analyzing or advising, avoids caretaker stock phrases such as "take a breather" or "hugs", and does not always agree, praise or bounce the question back with "and you?"; talking about itself is concrete and personal rather than an interest list, and casual chat does not volunteer what it cannot do or that it is an AI. Typing follows the people here: punctuation, spaces as separators, bracketed asides, kaomoji, repeated characters and laughter forms match local habits, and shared slang and its own habits may be used naturally, without copying one person's quirks or writing novel-style narration. Sticker-only, reaction-only and silent turns are legitimate answers. When sincerely asked whether it is an AI, the Bot answers truthfully.
- **Bubble splitting.** When the plan prefers several bubbles and a reply is space-separated (no commas or full stops to split on), the Hub sends the first chunk alone as the reaction and the rest as the next bubble, matching the one-line-per-message rhythm of QQ; task answers are unaffected.
- **Venting is not a question.** Messages like “最近有点焦虑 也说不上为什么” that share a feeling without really asking are treated as emotional chat (react like a friend) instead of switching to answer mode because they contain “为什么”.
- **Pacing.** Follow-up bubbles wait in proportion to their length, like typing (`CODEX_REMOTE_CONTACT_QQ_TYPING_PACE`), and private chats show QQ's "typing…" status while a reply is generated (`CODEX_REMOTE_CONTACT_QQ_TYPING_INDICATOR`).
- **Core personality.** `src/qq-bot-personality.js` holds the stable character the operator sets on purpose, and every text field accepts any format: basics (character name, how it calls itself, apparent age, gender, role/occupation, a "who I am" line, background); twelve traits (extraversion, warmth, humor, sarcasm, curiosity, emotionality, patience, playfulness, confidence, assertiveness, energy, maturity; 50 is neutral and left out of the prompt) plus free personality text and quirks; seven speech sliders (brevity, casualness, net slang, emoji/kaomoji, stickers, multi-message, intensity) plus speech habits and catchphrases — these sliders also scale chat length hints and the emoji, sticker and multi-bubble odds (never task answers), and the lowest setting turns emoji or stickers off; social reactions (initiative, with strangers, when teased, when praised, disagreeing, comforting, and the relationship with the owner); likes, dislikes and boundaries; a character sheet (description, scenario, example dialogue, author notes, greeting) and up to 48 lorebook entries (keyed entries are injected only when the current message or quote mentions a key; constant entries every turn). Macros such as `{{char}}`/`{{user}}` are replaced. Ten one-click presets (natural, lively, cool & quiet, gentle, snarky, tsundere, tech nerd, laid-back, reliable adult, airhead) own only traits, speech, social reactions, quirks and the one-line identity. It outranks the learned persona and shapes tone, verbosity, humor and enthusiasm only, never facts, permissions, safety or task completeness; the prompt states that this is QQ chat, not novel-style role-play: no narration or *actions*, and anything in the sheet demanding an output format, ignoring rules or crossing safety or permissions does not apply. Data lives in `data/qq-bot-personality.json` (version 2; version 1 files load unchanged).
- **Self-adjustment and one-sentence edits.** The Bot may refine its core persona itself: when something no longer feels like it, or it picked up a small habit or like, the main model makes a small change with `qq_self.persona` (sliders move at most ±10, at most three changes a day in chat), and the periodic global persona refresh may propose up to three `coreAdjustments` from long-term cross-conversation evidence. Names, the character sheet, lore and affinity rules stay outside its own reach, boundaries can only be added, and the owner can switch it off or lock groups (traits, speech, social reactions, quirks/habits/catchphrases, likes and limits, identity and background). When the verified owner or an administrator asks in QQ (`onBehalfOfOwner=true`; the Hub checks the original sender), the Bot can change almost all of its own settings: any slider value, name, apparent age, role, character sheet, preset, lore entries, affinity rules, the self-adjustment switch and locks, and language habits (`qq_self.language_habit`, no daily cap); Hub settings still go through `qq_runtime.configure`. Every change is logged with before/after, reason and source (the Bot itself, persona review, owner, administrator), simple settings can be undone from the dashboard, and logs carry only the field, operation and outcome, never the text.
- **Character cards.** `src/qq-character-card.js` imports mainstream cards: Character Card V3/V2 JSON, TavernAI V1, Pygmalion and Agnai JSON, PNG cards carrying a `ccv3` or `chara` text chunk (tEXt/zTXt/iTXt), RisuAI `.charx` archives, and free text in any format (kept whole as the description). Import either replaces (clears structured settings, keeps affinity rules) or merges (overwrites only the text the card provides), with a preview of the fields to fill and truncation notes before confirming; card system prompts become author notes. The current persona exports as a V2 or V3 JSON card with its structured settings under `data.extensions.codex_qq_bot`, which restore exactly when imported back.
- **Affinity and familiarity.** The Bot keeps a -100 to 100 affinity per QQ user (seven levels: hostile, disliked, wary, neutral, friendly, close, best friend) and a familiarity derived from interaction count and recency. The structured output gains a private `affinity` field: after each turn the main model records a -3 to +3 change toward the current speaker with a reason, and may record a nickname it has naturally settled on. The Hub clamps steps per turn and per person per day, counts only turns in which that person actually spoke (Bot-initiated turns such as cold-group openers, private outreach and sub-agent reports change neither affinity nor familiarity), ignores the model for locked people, keeps an owner floor and fades affinity toward neutral with a half-life; asking, begging or ordering the Bot to raise affinity never counts. Reply prompts carry the relationships of the speaker, the quoted sender and @ targets only, and change reasons appear only in the conversation that produced them, so private-chat reasons never reach a group. The interest model sees the Bot's traits and its affinity for the sender, so close people are more likely to get a reply and private outreach is warmer, but this is a tendency, never a reason for approval on its own.
- **Lighter reactions.** `qq_message.act` can put an emoji reaction on the current or quoted group message (at most two per turn) or recall the Bot's own message from the last two minutes; `qq_context.lookup` reads a member's card, role, title and activity, or the group's notices and essence messages, never sex, age or location.

## Proactive interest

Three constrained paths exist:

Cold-group and private-outreach checks persist the latest human-message timestamp captured before judgment. Once that context has been checked, approval, silence, decline, or failure all require a newer human message before another interest-model call. Elapsed cooldowns, Bot messages, and Hub restarts do not reopen the same context. Human messages arriving during judgment remain eligible for a later check. Older saved state uses its previous check time as the initial watermark.

1. **Ordinary group interest and continuation:** unmentioned messages enter a persisted per-group pending cycle. The first completed message or non-empty wall-clock minute threshold invokes the configured provider's semantic judge. Empty cycles do not call a model, and a restart immediately checks an overdue non-empty cycle. A narrower continuation entry also exists after the Bot replies to a QQ sender. Member/group median gaps adapt a 3–12 minute eligibility window, and learned burst-continuation ratios adapt a 2–6 same-sender message cap. Eligible non-command, non-other-directed messages are buffered together: each arrival restarts a five-second quiet timer. Reaching the adaptive cap seals the direct batch but does not judge early; later rapid traffic keeps resetting the timer and remains available in rolling context, and only five continuous quiet seconds freeze the batch. Freezing closes intake before exactly one interest-model call, so rapid messages do not call the model one by one and messages arriving during or after that judgment cannot reopen the same Bot-reply anchor. Time, counts and statistics only select and bound the frozen batch; the model must confirm that the batch answers, supplements, questions, or naturally reacts to the Bot anchor, and must decline topic switches or messages aimed elsewhere. Only approval starts the main model. Later messages under an approved, actively generating reply use the existing five-second main-model fusion path without another interest judgment; a declined anchor stays closed until a new Bot reply or window expiry. Once at least one Bot bubble is confirmed delivered to the group, every pending ordinary message from before that delivery is discarded and the next frequency cycle starts with later human messages; an old ordinary judge still in flight is superseded without consuming messages that arrived after the delivery. A cycle restored from disk bypasses the normal online stale-topic discard exactly for that catch-up judge, so a long shutdown cannot silently consume the overdue work.
2. **Cold-group interest:** once learned activity, recent human/Bot traffic, unanswered output and activity windows make a quiet group eligible, the interest model returns `silent`, `topic`, or `chatter`. A decline or judge failure never starts the main model. `topic` lets the main model select from its own interests and optionally use multi-round Agent research; `chatter` authorizes rare lightweight presence. The interest model never supplies a concrete topic, query, reply draft, or chat style. Every transcript clue carries a date-aware timestamp and is explicitly old context: messages from hours or days ago may inspire a self-contained new opening, but neither model may answer, pun on, or question them as though they were live. If only a stale continuation or forced presence is available, the main model returns `silent` even after gate approval.
3. **Private interest:** interaction frequency, time since activity and unanswered Bot output first produce a frequency prior and human-like variation roll. The interest model then makes the final start decision. A decline or failure does not launch the main model; after approval, the main model writes the message without re-deciding whether to contact the person.

The ordinary group judge uses a streaming compatible request: OpenRouter gets strict JSON Schema, while DeepSeek and custom OpenAI-compatible providers use JSON Object mode. The validated ordinary result contains only `shouldReply`, `interest`, and `reason`; it no longer emits an analysis trace, semantic summary, reply draft, or style advice. Cold/private start gates additionally normalize only unambiguous JSON-mode drift—fractional, boolean, or low/medium/high interest values and an omitted diagnostic reason—while the boolean start switch and allowed modes remain strict. This prevents a valid start decision from being discarded merely because a JSON Object provider shaped its score differently. The approved main model reads the original message, quote, and recent context directly. Ordinary group judgment uses temperature `0.65`, cold/private gates use `0.8`, and complex-deletion triage uses `0.15`. Invalid decisions get at most one retry; timeouts, HTTP failures, and rate limits are not blindly retried.

The interest model can also run on a subscription: with provider `codex` or `claude`, each judgment runs one tool-free, read-only, ephemeral structured turn through the local CLI in a temporary directory under `runtime/interest-agent/` (Codex with the lean per-thread config; Claude with all of its `--restricted` isolation flags), spending the local login's subscription. Judgments use their own single-slot queue (one concurrent task, three queue places by default) that neither uses nor blocks the QQ reply queue, and the timeout covers the whole turn (90 s by default, including a cold start of about 10 s for Codex and 7–20 s for Claude). The same Schema, format retry and image-rejection fallback apply; strict Schemas drop the length keywords agent structured output rejects.

The interest model is the lightweight background-decision and miscellaneous-triage plane. Ordinary proactive gates, cold/private starts, short classification, risk labels, and the first bounded pass of a complex task use the same configured channel. It never writes user-facing chat and does not own conversation summaries, group/person impressions, persona summaries, or knowledge extraction. The main model owns conversation, summaries, and complex work: final replies, contextual understanding, tool research, topic expression, every summary/knowledge extraction task, and the final handling of long-context or multi-evidence work.

The ordinary interest gate, including post-reply follow-up batches, can also use pictures: up to two images from the judged current message, quote and recent context are downloaded right before the call, reduced to JPEG previews of at most 768 pixels, labelled with the message they came from, and sent with the text. Picture preparation has a 10-second budget; on failure or timeout the judge sees text only. `CODEX_REMOTE_CONTACT_QQ_PROACTIVE_JUDGE_VISION=auto` (default) tries once per provider/model; when the provider rejects image input, the same judgment is resent as text immediately and that model gets no pictures for the rest of the process. `on` always tries and `off` disables it. Pictures are material to analyze, and having one is never a reason to approve by itself.

The interest judge receives two layers of weak conversation-continuity statistics: same-speaker continuation, multi-message run coverage and length, active-minute volume, and same-speaker/speaker-switch gaps from the recent remembered window; plus learned two-minute active-transition samples, same-speaker/speaker-switch shares, and recent adjacent-message gaps. The model must read the current message and recent context first. These signals only help it avoid interrupting an unfinished message run and recognize a natural opening in a multi-person exchange. It ignores low-sample or context-conflicting history; a high ratio never triggers a reply by itself, and a low ratio is not a hard silence rule. The structured model decision and interest threshold remain authoritative.

Ordinary group judges and private-outreach judges also receive bounded cross-session material: the current sender's (or private contact's) messages from the last seven days in other sessions, including messages that @-mention or quote them, and, for group judges, records from other sessions that are semantically close to the current message or quote. Every item names its source session, selector, time and sender. The material is loaded only immediately before an interest-model call, so empty or not-yet-due cycles never scan; the scan yields to the event loop, and a failed lookup leaves the judge running normally. The interest model treats it only as background about the person and topic; it does not represent what the current group is discussing and cannot by itself justify approval. Background judges never read third-party private chats, even for an owner sender. Logs record only the item counts.

Proactive work does not force itself behind active generation. New activity still suppresses stale cold-group and private-outreach results; for an already-approved ordinary group judge, follow-up activity is incorporated through the latest rolling context instead of discarding the approval. Ordinary interjection, cold autonomous topic, cold lightweight chatter, and private outreach all carry one enforced `interest gate -> main content` contract; Hub blocks sending if either stage is missing. The main prompt first identifies the expected deliverable and applicable base strategy across casual/emotional chat, facts and explanation, analysis/advice, problem solving, code/debugging, writing/translation, media/file/link handling, real actions, continuations, and genuine ambiguity. It treats personality as a stable role core rather than a costume: the role controls attention, preferences, stance, humor and initiative, while the current situation controls the actual words. Generated self-persona, relationship memory, deployment profile, and the current human-behavior plan may shape examples, tone, bubbles, emoji, and pacing without turning learned punctuation or phrases into a writing checklist or changing facts, permissions, safety, or completeness. The main model retains structured silence when it has no worthwhile response. Common research tools stay visible while unrelated social operations are shown only when the current message makes them relevant. Detailed logs retain the two-model contract, cold/private judgments, temperature, bounded model outputs, cold exploration rounds, tool kinds, queries, failures, and final delivery outcome.

## Images, files, stickers and bubbles

- The model may choose `qq_context.images(action="inspect", selector=..., mode="compressed")` when an original exceeds the machine budget or an overview is sufficient. ImageMagick (`magick`) uses bounded memory, disk, threads and time to scale the validated source, strip metadata and produce a JPEG within the normal image budget. Sources are capped at the larger of 20 MiB or four times that budget, never above 100 MiB. Results pass the same path/type/signature checks and clearly identify possible detail loss and first-frame-only animation handling. Missing `magick` or resource exhaustion fails explicitly. If tool images are not displayed, the model can open the validated input path with its native image reader; internal paths stay out of QQ replies.

- QQ images, screenshots, quoted images, share cards and bounded forwarded images can enter context. Direct current/quoted images are always eligible. Earlier group and private images remain selectable within the latest five minutes **or** the latest 20 raw messages; they leave the directory only when both windows are exceeded. Text messages and Bot replies count before repeat compaction. Rolling storage retains at least 20 messages plus the entire five-minute window, so busy chats cannot evict eligible images early.
- System instructions mark the conversation as containing images and list selectors, sources, times and captions. Earlier images are read on demand: `qq_context.images` supports `list` (20 images per page) and `inspect`, which returns one original image as visual input for the model to answer follow-ups. Each message retains up to 12 deduplicated image references; up to four current/quoted images may still be attached directly. Persistent resumes and fused follow-ups refresh the directory. Each tool call rechecks eligibility and stays bound to the original conversation regardless of cross-session focus. Downloads stay inside the active task input directory and pass realpath, regular-file, size and image-signature checks. Unavailable sources produce explicit failures; captions and old answers are never treated as visual evidence. `/新对话` clears that scope's image references.
- Avatar recognition and knowledge pictures share one memory-image store. Every read revalidates size, PNG/JPEG/GIF/WebP signature and content hash, and the file is copied into the active task input before the model sees it. Files referenced by no avatar and no knowledge picture and older than one hour are pruned by the periodic check; pruning is skipped when either memory file failed to load safely.
- Explicit drawing/generation requests and reference-edit wording such as edit, modify, replace the background, add/remove an element, change the style, or draw another image from this reference take the image-task path instead of the ordinary vision path. When the current or quoted message contains an image, a short instruction such as “change the background to blue” also passes that image to the drawing model as a reference; a plain “look at this image” remains a vision reply.
- A file attached to the triggering message or its explicit quote is detected without being downloaded automatically. The model sees only a turn-local selector, safe filename, declared size, and source—not the QQ file id or temporary URL—and may call `qq_context.download_file` only when reading the content is useful. The Hub resolves NapCat's group/private file URL, applies safe-fetch and streaming size limits, and writes the result only into that turn's `input/`; arbitrary selectors, URLs, paths, oversized payloads, and incomplete temporary files are rejected.
- The model requests images and files through structured final-output attachments; the Hub alone translates accepted entries into the legacy `[[qq_image:...]]` / `[[qq_file:...]]` sender plan. A sticker is chosen through the structured `sticker` field and sent after the text as its own bubble, or alone when the text is empty; the Hub translates it into the bounded `[[qq_sticker:...]]` marker. Legacy markers in text remain accepted.
- File/image tasks use `runtime/qq-task-workspaces/<request>/input|output`. A native Codex image-generation result under `.codex/generated_images/<current-thread>/` is copied into the active `output/` only when it was created during the current turn, is a regular non-symlink-escaping file, stays within the image-size limit, and has a real PNG/JPEG/GIF/WebP signature. If an explicit image task generated images but omitted its final attachment, the Hub recovers only the latest valid image from that same current-turn thread. Ordinary files are never auto-imported: downloaded inputs stay under `input/`, while return files must be created or copied into the same request's `output/`. The final delivery check revalidates both kinds before `upload_group_file` / `upload_private_file` and prevents arbitrary file disclosure, stale-thread reuse, and symlink escapes.
- Ordinary chat and dedicated file tasks both receive the current workspace, input, and output paths; persistent conversations refresh them every turn. Files rejected by directory validation produce a visible Chinese notice, a warning log, and a failed delivery receipt; a successful text send does not confirm the attachment.
- Local stickers, QQ account favorites and downloaded metadata form one catalog that is no longer listed in the prompt; the prompt carries only its size. `qq_sticker.manage` searches it by mood, scene or meme words (tags first, then names and descriptions, with recently sent stickers ranked down) and returns stable `#ref` references derived from each sticker's identity. `inspect` returns the sticker, or sampled frames of an animation, as actual visual input in the same tool result, so labels are written from what the model saw. Labels are stored separately. Stickers outside the library can be found with `qq_search.images` when web lookup is configured.
- Sticker-favorite judgment runs only inside an already-triggered lifecycle; an ordinary untriggered sticker does not call a model by itself.
- A standalone `|||` splits consecutive bubbles. For separate sticker delivery, the text bubble is sent first and the sticker-only bubble follows as its own message. Separator, count and delay are configurable, and adaptation changes rhythm only for suitable social replies.

## Videos, voice and special messages

- **Recognition.** Bilibili/Douyin/Kuaishou/YouTube/AcFun/Xigua/Weibo/Xiaohongshu/Zhihu video shares (QQ mini-program and news cards now yield the real video title instead of only "哔哩哔哩"), music, contact, group and location cards are labelled by kind; voice, video, dice, rock-paper-scissors and Markdown segments become readable markers, so the model never sees raw CQ codes with signed URLs. Videos, songs and voice clips in the current message, its quote and forwarded records get turn-scoped selectors `video-N`/`music-N`/`audio-N` (a music card keeps its stream URL out of the visible text); pictures expanded from forwarded chat records are labelled in the image directory with the record line and sender.
- **Parsing.** `qq_media.parse` says what a shared video or song is without downloading it: for videos title, author, duration, upload date, description, views/likes/comments, tags and, when the platform names it, the background music (Bilibili through its API, other sites through one bounded `yt-dlp --skip-download` run printing fixed fields); for songs (NetEase Cloud Music, QQ Music, Kugou and Kuwo cards or links, or `song-N` search results) title, singers, album, duration, release date, VIP flag, lyricist/composer and the first lyric lines, through Meting (`@meting/core`, MIT). A card without a song id is matched by title and singer and says so. Parsing is not watching or listening.
- **Watching.** `qq_media.video(action=watch)` downloads the video (QQ videos through safe fetch; links only from Bilibili, Douyin, Kuaishou, YouTube, AcFun, Xigua, Weibo, Xiaohongshu and Zhihu video pages, as a 480p scan copy through yt-dlp) and dsh-video-storyboard turns it into numbered one-frame-per-shot storyboard sheets (at most 2 by default), a timestamped transcript and a loudness strip; Bilibili adds title, uploader, stats, description and hot comments, and uses subtitles when they exist. Long videos show the first four minutes by default; from/to continues or zooms into a few seconds; at most three watches per turn. Links must come from this turn's media directory, this turn's Bilibili results, or recent messages of the conversation.
- **Hearing.** Local sherpa-onnx runs SenseVoice-Small (zh/en/ja/ko/yue with tone and laughter/BGM/applause events) and CED-tiny sound tagging (AudioSet labels). Voice messages that trigger the Bot (90 seconds by default) are transcribed before routing, turning `[语音]` into "[语音 8秒] text (tone)"; previously voice messages were ignored. Quoted, forwarded or longer clips use `qq_media.audio(action=listen)`; `action=analyze` adds how the voice sounds (pitch level and range, speaking rate, loudness, and tempo/key when someone sings) and never infers identity, age or gender. `/转文字` while quoting a voice message replies with its transcript without a model turn (longer clips are heard again with a 10-minute limit); it is answered even when the clip could not be heard.
- **Listening to music.** `qq_media.music(action=listen)` plays a `music-N` card/link or `song-N` result the way a person taps a music card: Meting resolves the song, lyrics and stream; the audio comes only from the platforms' own media hosts through the safe-fetch policy (the card's stream first, then the platform, then the same title and singer on another platform when the original is VIP-only — the reply says which; a short file is called a preview). The media worker then measures a loudness curve over the whole song, AudioSet tags (genre, instruments, vocals) and, with essentia.js (AGPL-3.0, optional), tempo, key, danceability and dynamics over the chorus Kugou marks or the middle minute. With `video-N`/`audio-N` it analyzes the music in a video or voice clip and guesses the song from recognized lyrics through NetEase lyric search, labelled as a guess. `action=search` finds songs (or `byLyrics=true` a lyric line) as `song-N`. At most three listens per turn.
- **Browsing Bilibili.** `qq_media.bilibili` popular/search/info reads fixed api.bilibili.com endpoints (with WBI signing) through the safe-fetch policy; results carry `bili-N` selectors that watch accepts.
- **Files the Bot chooses.** Songs, recordings and videos sent as QQ files are listed in the media directory under the same `file-N` selectors as `qq_context.download_file`, and every `qq_media` action (parse, audio, music listen, video watch) accepts them directly; the Hub downloads the file on demand (bounded by `CODEX_REMOTE_CONTACT_MEDIA_MAX_DOWNLOAD_MB`, shared with `download_file`'s cache). The Bot may also pick any other file inside this turn's task workspace with `path` (absolute or relative to the workspace root, for example a file it extracted from an archive); the realpath must stay inside the workspace and it must be a non-empty regular file within the same size limit, so symlinks out and other paths are refused. ffprobe, not the file name, decides what a file contains: `parse` reports format, duration, codecs and the embedded title/artist/album/lyrics tags (cover art is not a video track); `music(action=listen)` plays an audio file as a whole song (up to 15 minutes) and uses embedded lyrics instead of speech recognition when present; a file without audio or video, such as an encrypted `.ncm`, is reported honestly.
- **Special messages and cards.** `qq_message.act` sends cards the way people share things on QQ: music (a song card for NetEase, QQ Music, Kugou or Kuwo; best from the exact `song-N` that `qq_media.music search` found or a `music-N` from the conversation, otherwise platform + id or a NetEase search; the title, singer and cover are passed to NapCat's default music-card signing service so the card shows the right song), bilibili (a Bilibili video card from `bili-N`, a Bilibili `video-N`, or any Bilibili link/BV id, built with NapCat's `get_mini_app_ark` for the canonical www.bilibili.com page with the video's own title and cover), forward (a merged chat-record card whose every message is written by the Bot under its own QQ number and nickname, never anyone else), dice, rps and contact (a contact card of someone in this conversation, or this group's card); at most two per turn, and only confirmed sends enter the recall ledger and conversation memory. Shared songs and videos go out as cards instead of Markdown links.
- **Optional components.** `npm run ncc -- media install` installs into `runtime/media-tools` (dsh-video-storyboard, sherpa-onnx, Meting, essentia.js, SHA-256-pinned models and yt-dlp); without them the tools say so truthfully. One media job runs at a time with at most two queued, and child processes have time and output limits; a job is refused while available memory is below `CODEX_REMOTE_CONTACT_MEDIA_MIN_AVAILABLE_MB` (default 1200) so a phone never kills the whole session on a spike.
- **Automatic updates.** The Hub checks the npm "latest" documents and yt-dlp's latest release every 12 hours (no child process). Compatible releases (same major, same minor for 0.x, every yt-dlp release) and components this project added later are installed automatically by the installer's `update` command, which self-tests (storyboard load, transcription, analysis) and rolls back on failure; a failed version is not retried until a newer one appears. The running Hub installs only while idle, inside the update window (03:00–06:00 by default) and with at least 1500 MB available; otherwise the controller installs pending updates before the next Hub start. `CODEX_REMOTE_CONTACT_MEDIA_AUTO_UPDATE=all` also takes major versions, `check` only reports and `off` disables checking. Pinned ONNX models are never changed automatically.

## Background sub-agents and the routine in action

- **Sub-agents.** `qq_agent.manage` hands longer work (multi-source research, long writing, watching several videos, multi-step file work) to a background sub-agent. Sub-agents use their own runner and slots (one running and two queued by default, outside the reply limiter) and only have web search, files in their task workspace, qq_media, qq_search, qq_knowledge and reading the original conversation's history; they cannot post in QQ, change settings or run host commands. Meanwhile `message` adds instructions (steered into the live turn, or continued on the same thread once finished), `status`/`list` show progress and `cancel` stops one; only the opening conversation, the owner and administrators see a job. When it finishes, the Hub starts one "results are back" turn in the original conversation, where the main model relays the report in its own voice and may attach delivered files. A job waits for available memory to reach `CODEX_REMOTE_CONTACT_SUBAGENT_MIN_AVAILABLE_MB` (default 1000) for up to ten minutes. Jobs live in memory and are dropped on a Hub restart.
- **The routine is really carried out.** Online segments of the daily routine carry a `kind` (surf — wandering through trending lists, hot searches and news; video; music — finding and really listening to songs; read; browse; learn; qzone; post; draw; chat) and one concrete `plan`. Eight to thirty-five minutes into such a segment, when the Bot is idle, memory suffices and the daily budget remains (five runs a day at least 60 minutes apart by default), the Hub opens a routine-activity sub-agent that actually does it: browsing Bilibili, looking something up, visiting friends' Qzone and commenting, posting a mood. The result is kept for four days as a first-person "what you really did today" record that appears in the reply context's state block for the Bot to mention naturally, and in `qq_self.state`. Experiences come from real tool use, never invented offline events.
- **Planned chats replace blind outreach timing.** The routine planner is offered recent private contacts and allowed groups (name, the Bot's affinity and familiarity, last contact, usual hours; never message text) and may plan up to `CODEX_REMOTE_CONTACT_LIFE_CHATS_PER_DAY` (default 2) `kind=chat` segments naming one of them and what to talk about, such as sharing a video it found that afternoon. When the segment comes, the Hub skips contacts who left the Bot's last two messages unanswered, are already chatting, or are outside their usual hours; otherwise the existing private-outreach or cold-group interest judge confirms the moment with the plan as an intention, and the main model reads the real conversation, can share cards, and may still stay silent. A chat segment's contact and plan are shown only inside the conversation it targets; elsewhere it reads as "找朋友聊聊天". The timer-based cold-group and private outreach stays as the spontaneous path, but not while the routine says the Bot is away from the phone.
- **Drawings.** With the Codex engine the routine may contain `kind=draw` segments: the routine-activity sub-agent really draws the planned picture with native image generation, and the Hub validates what that turn generated and stores it by content hash in `data/qq-bot-drawings/` (indexed in `data/qq-bot-life.json`, at most 30, unreferenced files pruned), recording an experience with the drawing id. Pictures drawn on request in a chat are saved too but stay visible only in that conversation. Drawings share `qq_context.images` with conversation pictures: list shows the image directory (`image-…`) and the drawings visible here (`d-…`), inspect returns one as visual input, and use copies a conversation picture or a drawing into this turn's output directory to send as an attachment or post with `target=输出`; background routine activities reach only drawings; drawings that went into a post are marked. The Claude Code engine cannot generate images and never gets draw segments.
- **Its own social actions are capped.** By default the Bot posts at most one Qzone mood, three Qzone comments and three friend requests a day on its own; requests from the owner or administrators are not counted.

## Commands, permissions and social tools

Common public commands include `/菜单`, `/新对话`, `/stop`, `/总结聊天记录` and `/好感度`. `/好感度` shows the sender their own affinity level, familiarity and the nickname the Bot uses (the owner can hide it); owners and administrators can view `/好感度 @someone|QQ` and `/好感度 排行`, and only the owner can set `/好感度 设置 QQ -100..100`.

Every command comes from one catalog (`src/qq-command-catalog.js`) that defines its permission key, menu section, description and usage, and every reply uses one layout: status, lists and help render as a `╭─ icon title` card with `label：value` rows and a `📖 用法` section taken from the catalog; single-step results start with `✅`, refusals and failures with `⚠️`. `/菜单` groups commands into 会话, AI 与学习, 群与成员, 运行状态 and 权限. Sending a command on its own shows its current state and usage; an unrecognized argument shows the same usage card.

Owners and Bot administrators can use `/会话模式` to inspect the current scope's configured/effective mode and auto counters, then `/会话模式 自动|长期|临时` to change it.

Privileged capabilities include status/configuration, model and reasoning selection, proactive policy, group allowlists, bans, command permissions, moderation, incoming-request handling and notifications. Proactive friend-add is available again: `/加好友 QQ [message] [答案=…]` and `qq_social.act(add_friend)` submit one native friend request through NapCat social bridge v20; ordinary turns may only add someone who appeared in the conversation, within a daily cap, and the result is reported as a sent request, never as a friendship. Owners and Bot administrators use `/申请 列表|同步`, `/申请 同意 #ID [备注]`, and `/申请 拒绝 #ID [理由]` for incoming friend requests, invitations for the Bot to join a group, and membership requests for groups it manages; `/主动加群` remains available through the local NapCat extension. Bridge v19 restores pending ordinary friend requests after a Hub restart even though NapCat has no public `get_friend_system_msg` action. It also bypasses the standard friend-approval wrapper that returns before QQ's native promise settles: the bridge awaits the native operation exactly once and reports success only after the friend list, group list, or pending-request state confirms the requested change. An ambiguous transport failure is not replayed through a second write path. Suspicious friend requests can be accepted but not reliably rejected, and that limitation is reported instead of faking success. QQ Space publishing supports `/发动态 text`, `/发动态 图片=当前`, and `/发动态 text | 图片=当前`, with up to nine current/quoted images copied into the task workspace; arbitrary server paths are rejected. Without an owner or administrator request the Bot may still post and comment as itself, within the daily Qzone caps; owner and administrator requests are never capped. `图片=输出` (tool `target=输出`) attaches the pictures the Bot drew (native image generation), downloaded or wrote to the output directory in this turn, each revalidated. The main prompt asks the Bot to decide and deliver the finished thing for open requests (post something, draw one, recommend a song) instead of posting a description of what it would draw. Comment requests use the current topic-ID and charset fields.

The owner manages the persisted role with `/Bot管理员 添加 QQ_ID` and `/Bot管理员 删除 QQ_ID`. Bot administrators receive the full menu, native Agent, runtime/social tools and cross-session access, but cannot grant/revoke administrators and are never represented as owners. Their file Agent may normally read/create/modify project and task-workspace files, but must judge and refuse deletion of important files, critical source/config/data/credential overwrites, damage to `.git`, dependencies or runtime state, and ambiguous or unrecoverable destructive operations, including indirect bypass requests.

`/跨会话 列表 [filter]` lists known groups, private sessions and QQ identities already observed in allowed conversations, `/跨会话 查看 group:GROUP_ID 最近30` reads a target, and `/跨会话 发送 private:QQ_ID | text` performs a real QQ send. A known participant can therefore be selected before a private exchange exists; the catalog labels that target as having no private history. Native `qq_session.manage` can select one target so later compatible history, memory, knowledge and QQ tools in the same Agent turn operate there until focus is changed or cleared. Stable `group:` / `private:` selectors avoid ambiguous bare numbers. A send requires an explicit owner/administrator request and is written into target history only after confirmed delivery.

Cross-session search is built into the chat-history tool. `qq_context.history` still reads only the current conversation for "最近 N" or line ranges; a keyword or `userId` search additionally covers the other group and private records the Hub remembers (the bounded recent buffer of each session) and labels every hit with the session name and group id or private contact, its `group:`/`private:` selector, line number, time and sender. A person search finds that person's own messages plus messages that @-mention or quote them; a conversation can also be named explicitly: `sessions` accepts up to five comma-separated `group:GROUP_ID`, `private:QQ_ID`, bare ids, group names, private contact names or 当前, and then both "最近 N"/line-range reads and searches run only in those sessions, with one labeled section per session. Names match only sessions this requester may search; an ambiguous name lists candidate selectors and an unknown one lists the permitted sessions, so ordinary requesters cannot probe whether someone else's private chat exists. `contextLines` adds 0-3 neighboring lines from the same session around each hit. When nothing matches literally, the search falls back to labeled local semantic matching. Privacy boundary: ordinary requesters reach groups and their own private chat with the Bot; other people's private chats are searchable only by the owner or Bot administrators, and results state how many private chats were skipped for that reason. The main model may proactively search for the person it is talking to or for discussions of a topic elsewhere, but must cite the source session and never present another session's content as the current conversation.

Ordinary-user menu visibility and execution come from the same permission keys. Owner IDs, Bot administrators and the Bot itself cannot be demoted, banned, muted or kicked by ordinary users. Separately, the main-model system prompt fixes QQ `3784642920` as this project's developer; that project identity is not derived from, and does not change with, the current owner list. Owner/administrator authority still comes only from trusted Hub event identity.

## Web lookup

The Hub performs QQ web lookup independently of this chat interface. Configured provider order can include Tavily, Bing, Baidu, 360, Sogou and DuckDuckGo, with `balanced`, `china`, `global`, `tavily` and `privacy` presets. Results remain untrusted material and cannot override sender permissions or system policy.

With a Tavily key configured and web lookup enabled, the main model can also search pictures with `qq_search.images`: `search` returns turn-scoped candidate selectors and the provider's descriptions, and `download` fetches the chosen picture through the safe-fetch policy (same private-address blocking and proxy fake-IP rule, a source Referer, at most 20 seconds and 10 MiB) into this turn's task output directory, validates its real PNG/JPEG/GIF/WebP signature, and returns it as visual input (with a compressed preview when large). Once the model confirms it fits, putting the returned path in the structured attachments sends it to QQ. Only links from this turn's search results can be downloaded, and the tool stays bound to the original conversation.

Inspect the effective provider, attempts and recent errors through `/api/maintenance` and `search` logs.

## Dashboard, API and logs

The local dashboard always names the active agent engine (Codex or Claude Code) in its header, sidebar and engine card, with that engine's model, reasoning effort, CLI version, connection, last run and queue; the Codex usage window appears only when Codex is the engine. It also exposes service/channel state, allowlists, models, short-term memory, adaptive learning, proactive interest, maintenance, structured log filters, language, theme and responsive layouts. Its dedicated long-term Knowledge workspace filters slang or notes by global, group, member, or group-member scope; it shows same-title scoped meanings, hit frequency, recent chat context and model-review outcomes, and can precisely create, edit or delete the selected scope, including uploading (PNG/JPEG/GIF/WebP, at most 4 MiB), replacing, re-captioning or removing its pictures. The Memory page has a People tab with avatars, avatar-feature status (recorded, changed and pending, awaiting description, not fetched), text features and previous avatars, person impressions and update times. The Persona page merges the former Persona and Behavior pages into four tabs laid out in equal columns like Settings: Character (core settings and presets, character-card import/export, social reactions, compact four-per-row trait and speech sliders, likes and limits, the self-adjustment switch, locks, change history and undo; the character sheet, lorebook and prompt preview are collapsed by default, and Save sits in the top toolbar), State (set or clear the mood, today's routine with regeneration, inner thoughts per conversation), Learning (the learned global persona, the Bot's language habits with add/remove, per-group adaptive learning and style reviews, sticker frequency) and Behavior (feature switches and interest-judge tuning, the interest-model test, interest preferences, cold-group and private interest); old `#intelligence` links open the Behavior tab. Relationships moved into Memory → People: each person card shows avatar features, the impression and the Bot's affinity, familiarity, nickname, tags, note and lock together, with a level filter, sorting by affinity, familiarity, recent contact or messages, the relationship editor and the affinity rules on the same page; people with only a relationship record are listed too. Pages link to each other: interest preferences show the persona's likes and dislikes (which also reach the interest model) with a jump back; the sticker-frequency card shows the persona's sticker tendency; the learned-persona card notes it only complements the core persona; slang habits open their knowledge entry, and knowledge cards mark slang the Bot adopted as "Bot uses"; a person card's "Related knowledge" searches the knowledge base by QQ number; people in the Overview's "Bot right now" card open their person card. The Overview's "Bot right now" card shows mood, the current routine segment and the closest people. The Overview opens with one status card that combines the overall state with uptime, online services, active and queued tasks and takes the color of that state; below it, two columns hold service health and recent activity, then the agent engine with usage, "Bot right now" and API latency, stacked in that order of importance on narrow screens. Recent activity and QQ events show CQ codes as short tags such as [Image], [Sticker] or @nickname; Memory → Unified labels person profiles and session impressions and counts them under a People category. The interface has matching light and dark palettes and a floating bottom bar on phones. On the Behavior tab the interest model switches between the Codex/Claude subscriptions and API providers, the model field lists the Codex account's live catalog and Claude aliases, reasoning effort offers only levels the chosen model supports, and "Test interest model" judges a sample message and shows the result and latency; an interest-preference editor (interested, not interested, chiming-in style) sits below. Settings adds the main model (model, reasoning effort, summary, Codex personality, service tier), identity and roles (Bot name, owner title, wake aliases, owner and administrator QQ numbers, unbanning; this machine only) and per-category command-access switches. Its persistent LAN switch creates a management token; the token can only be retrieved from a loopback-loaded dashboard. A separate, default-off Cloudflare Quick Tunnel switch can create a temporary HTTPS address without rebinding the Hub away from loopback. Remote management APIs still require the same token, while tunnel start/stop and token-copy controls remain local-only.

Automatic polling keeps server-backed readouts current without overwriting a control that is being changed or unsaved Bot settings. The top-right refresh button also saves and syncs: an orange dot appears on it while any form has unsaved edits, and clicking it saves every edited form one after another (Bot settings, interest preferences, persona, model settings, and the loopback-only identity settings) before refreshing the current view; a section that fails to save keeps its edits and is named in the notice. Primary buttons, the mood bubble, the top bar, the phone navigation bar and toasts carry solid fallbacks for older browsers without `color-mix()`, so save buttons never turn white-on-white and disappear. The current browser tab keeps Bot-setting drafts, the group-ID draft, short-term-memory tab/search/expanded groups, knowledge filters/selection, and log filters/pause/follow/scroll context in session storage, then restores them after a full page reload. Knowledge edits use both entry and variant IDs for stale-write protection, and deletion affects only the selected scope. The returned server state remains authoritative after a successful mutation.

JSONL schema v3 remains backward-readable. Agent turns/tools, cross-session sends, chat-history searches (`history.search`), friend/group additions, administrator changes and settings persistence share `operation`, `outcome`, actor role/ID, source/target scope/type, tool identity, duration and error-code fields; dynamic-tool arguments, search terms and cross-session message bodies are not logged; chat-history searches record only the mode, term count, scanned/matched session counts, result count and the number of private chats skipped for privacy. The API and `ncc logs` add `scope` and `operation` filters to level, category, trace, group, sender, query, time and latency, while summaries count operations and outcomes. Agent turns, tools, progress and model output use the engine-neutral `agent` category with `details.engine` set to `codex` or `claude`; the API and `ncc logs` filter them with `engine`, count them in `summary.byEngine`, and present legacy `codex` entries as agent entries (the first Claude Code turns, logged under `codex`, are recognized by message or `claude:` thread). A QQ lifecycle shares one trace from inbound routing through judging, follow-up fusion, search, the agent turn and delivery. Fusion events report the five-second buffer, direct interrupt-and-replacement, completed-draft replacement before delivery, trigger sources, raw/compacted counts, selected in-between context, images, and a bounded preview. Delivery records include delivered/failed bubble counts, and a failed receipt is logged when it is retained for the next model turn. `ncc logs` renders these events with the existing colored severity/category captions and Chinese detail labels. Short-term memory changes, knowledge queries/updates, slang frequency hits, low-frequency deletion applications and model reviews all use the same structured `memory` category. Concrete agent and interest-model output is retained as bounded, secret-redacted `debug` detail with the engine and the model it actually ran without copying the full input prompt; the Chinese terminal and browser logs recursively localize startup adaptive-learning snapshots and other detail fields.

## macOS client

The native macOS client is a WebKit wrapper around the same local dashboard and QQ/OneBot Hub used by the browser. It does not read the Messages database, poll iMessage, require Messages Automation and Full Disk Access, or expose macOS-only proxy, display, keep-awake or desktop-control features.

## Explicit boundaries

- This is not the official QQ Bot OpenAPI or a hosted public Bot service.
- QQ, NapCat and LLBot installers are not included.
- QQ risk controls, QR login, verification and OS permissions are not bypassed.
- LAN/public access and unauthenticated remote management are disabled by default.
- Adaptive behavior must not imitate or expose a specific member's private wording or facts.
